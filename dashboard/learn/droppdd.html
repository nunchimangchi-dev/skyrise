droppdd

Not a tool this setup depends on — the first real project built with it.

What it is

droppdd is a fitness/coaching web app (keto, OMAD, guided workouts, AI meal planning), built as a Next.js project. Unlike every other entry in this dashboard, it isn't infrastructure — it's the thing all the infrastructure exists to support.

Why it's here

Every tool above (git/GitHub, tmux, fish, Bitwarden, chezmoi, Tailscale) can look fine in isolation and still fail once something real is built on top of it. droppdd was scaffolded specifically to stress-test the whole toolchain end to end — new repo, SSH push, CI lint workflow, running its dev server inside a tmux window — instead of taking it on faith.

What you'll use it for

This is where day-to-day development work actually happens going forward. Its dev server runs in the droppdd tmux window (see the tmux page), it's pushed to GitHub the same way as skyrise, and any future secret it needs (like an AI API key) comes out of Bitwarden, never committed.

Testing it yourself, step by step

This is the sequence used to verify every feature before it's called done — worth running through yourself so you can speak to it in an interview without needing to take it on faith.

  1. Build it first. npm run build — this catches type errors and broken routes before you even open a browser. A clean build is the first bar, not the last one.
  2. Run it locally. npm run dev starts on localhost:3000 (the live deployment runs separately on 3001 via systemd, so dev and prod never collide).
  3. Sign in for real. Google OAuth, gated by the AllowedEmail table — there's no test/mock login. If your Google account isn't already on the allowlist, add it via npx prisma studio first.
  4. Click through every page, not just the one you changed: Dashboard, Workouts, Meals, Progress, Wagers. A change to shared code (auth, the Navbar, the Prisma schema) can quietly break a page you didn't touch.
  5. Verify against the database directly, not just what the UI shows — the UI can look right while nothing actually persisted. sqlite3 prisma/dev.db "select * from Wager;" (swap the table name for whatever you're checking) confirms the write actually happened.
  6. Test the failure path, not just the happy path. For Wagers specifically: try creating one with an unsafe weight-loss target (more than ~1% bodyweight/week) — it should be rejected with a plain-language error, not silently accepted or a crash. That guardrail is the actual point of the feature.

Talking points if asked "walk me through this"

The Wagers feature (shipped 2026-08-19) is a good one to know cold: Progress/WeightRecord were originally global, unscoped tables — a real data-model bug hiding in plain sight because the app only ever had one user. Fixing it meant a hand-edited SQLite migration to backfill existing rows to the real user before making the column required, plus a new session-based auth gate on the Progress page that didn't exist before. That's a concrete example of a change that looked small on the surface (add a feature) but required understanding and fixing something underneath it first.
